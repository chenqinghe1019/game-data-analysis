# 游戏数据分析工作流

1. 把问题落成可核对的范围：游戏和项目、市场、渠道和端、区服、用户粒度、时区、活动节点、窗口、截至完整数据日、指标分母、纳入和排除条件。采用用户最近确认的设置。复盘先输出结论页，口径变化随结果记录。
2. 优先复用用户指定的数数 TA 看板和原报表、AppLogger 原始导出及已验证 SQL。保留项目、看板/报表名、SQL 版本或查询 ID、筛选条件、抓取时间和数据截止日。选择器需确认实际选中，避免只展开或只高亮。按日拉取并保留日期、端、区服、玩法或商品等粒度；导出后检查表头、覆盖范围与记录数。来源不可读时注明具体缺口，用现有源推进可做部分。
3. 前后对比锁定相同口径、相同天数和窗口位置。赛季或多期活动用相对上线日对齐。前后 7、20、21 天均为历史任务示例，采用当前任务窗口。当天或回访尚未成熟时标识临时快照或待观察。按业务时区确认完整入库后的最后一天。故障、停服、阶段性投放分别列示原口径及敏感性对照。
4. 先核对整体，再拆至批次、区服、端、玩法、VIP 或商品。以人数、金额、次数等原分子分母重算合计。账号可跨端、跨服时按业务粒度去重，无法验证时标注分端或分区服相加的口径。空白、零、无数据、不可比和未成熟使用可区分的标记。
5. 复拉或修改口径时，核对游戏、源报表、批次、日期、条件、商品 ID / 分类、单位、金额单位、分母和数据刷新时间。核对原始日数据与汇总、明细与大盘、子组与合计，记录无法对平的差额和原因。
6. 首页把主要发现写成可直接转述的中文。先给方向和量级，再点名贡献最大、拖累最大或例外分组，最后说明证据和可执行动作。复盘按“发现问题 → 推动优化 → 落地结果”组织，清楚区分事实、归因假设、待验证方案、已发生结果。

指标口径和 Excel 交付检查见 [指标与交付](references/metrics-and-delivery.md)。专项分析结合对应技能：SLG 上线/合服、保卫萝卜 4 三端、埋点与看板、活动与商业化复盘。通过已有授权工具访问数据或看板。

历史材料见 [知识来源](references/sources.md)。

- 本次分析中用户明确确认有长期复用价值的指标、字段、筛选、看板步骤、SQL 实现或交付习惯后，同一会话检查现有知识，直接提交对应 GitHub 知识文件并验证提交。适用于游戏数据分析的长期业务知识，包括项目专用口径。
- 若修改影响插件本身的工作流或随附示例，结合当前插件版本更新对应技能或参考文件；仓库 Canonical 文件是业务口径的来源。回复注明已提交位置或遇到的实际阻碍。
