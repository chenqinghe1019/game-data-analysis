# 下方了直播包及转端 LTV / ROI 口径

更新时间：2026-09-15

## 统计主体

- 统一以 `nb_open_id` 作为唯一玩家主体。
- 用户来源渠道 `active_channel`：同一 `nb_open_id` 在 `ta.v_user_41` 全量角色中，最早 `create_role_time` 对应的 `channel_id`。
- 行为渠道 `event_channel`：玩家实际 `in_out_log.channel_id`。
- 渠道新增日期：同一 `nb_open_id × event_channel` 第一次出现该行为渠道 `in_out_log` 的日期 `first_logindate_channel`。
- 首次渠道与首次进入渠道都必须先扫描完整历史，再应用看板日期筛选；当前历史起点使用 `2025-10-16`。

## 端包范围与筛选（2026-09-15 最新）

不再在 LTV / ROI 主看板中使用“微端包ID”参数 `${Text:text1}` 过滤，也不再使用“用户来源ID”参数 `${Text:text2}` 过滤。

端包集合统一动态读取：

```sql
SELECT DISTINCT cast(channel_id AS varchar)
FROM ta_ext.channel_id_41
WHERE channel_type IN ('官方Android渠道','官方Apple渠道')
```

即当前所有 `channel_type = 官方Android渠道 / 官方Apple渠道` 的包都自动进入统计，后续新增同类型渠道无需再改 SQL 的硬编码 ID 列表。

渠道名称同样从 `ta_ext.channel_id_41` 获取；JOIN 前按 `channel_id` 去重，避免渠道维表重复导致流水膨胀。

## 两种用户类型

只统计以下两类：

1. `转端用户`：`active_channel = 3056211`（微信小游戏），且实际进入上述动态端包集合中的某个 `event_channel`。
2. `端包用户`：`active_channel` 本身属于上述动态端包集合，且实际进入上述动态端包集合中的某个 `event_channel`。

不再输出“用户来源ID”维度；报表保留“微端包ID / 微端包名称 + 新增类型 + 媒体平台”等维度。

分类依据始终是“首次注册来源渠道 + 实际行为渠道”，不是比较不同角色的端包创角时间，也不是用支付渠道反推用户类型。

## 媒体平台

- 媒体平台取 `ta.v_user_41.ad_platform`，按同一 `nb_open_id` 最早 `create_role_time` 对应角色取值。
- NULL / 空字符串统一为 `natural`。
- 保留 `${Text:text3}` 媒体平台筛选。
- 保留媒体明细行和 `媒体平台=汇总` 行，媒体汇总发生在媒体筛选之后。

## LTV

- 按 `nb_open_id × event_channel` 统计。
- 支付事件：`ta.v_event_41.pay_log`。
- 有效支付：`payment > 0`，不限制 `pay_result`、`change_reason`。
- 金额单位：`payment / 100` 转元。
- 从渠道新增日起，只统计同一 `nb_open_id` 且 `pay_log.channel_id = event_channel` 的支付。
- 支付渠道也必须属于上述动态端包集合。
- `端包用户`流水原值；`转端用户`流水乘 `0.4`；人数不打折。
- 输出 `LTV1~LTV180`；`LTVn` = 渠道新增日起第 1~n 个自然日折算累计流水 / 渠道新增人数。
- 支付最长扫描到 `渠道新增日期 + 179 天`。
- 每个 `LTVn` 单独成熟：`渠道新增日期 + (n-1) <= 昨天`，未成熟返回 NULL。
- 保留 `新增类型=端包用户 / 转端用户 / 汇总`。
- 新增类型汇总分子 = 端包流水原值 + 转端流水×0.4；分母 = 两类新增人数原值。
- 保留 `渠道新增日期=汇总` 行；日期汇总 LTV 不做每日 LTV 算术平均，而按成熟 cohort 的 `折算累计流水合计 / 成熟新增人数合计` 计算。

## 留存

- cohort 与 LTV 一致：`nb_open_id × event_channel`。
- 留存只认同一 `event_channel` 的 `in_out_log`。
- D1 = 渠道新增当天；Dn = 渠道新增后第 n 个自然日。
- 每个 Dn 单独判断成熟；未成熟返回 NULL。

## ROI

- ROI 分子与 LTV 流水一致：同一 `nb_open_id × event_channel` 累计支付，端包原值、转端×0.4。
- 输出 `ROI1~ROI180`，支付最长扫描到 `+179天`。
- 每个 ROIn 单独成熟；未成熟返回 NULL。
- 若某个日期汇总维度在 ROIn 下没有任何成熟 cohort，则该 ROIn 返回 NULL，不显示伪 0%。
- 保留新增类型明细与汇总、媒体明细与汇总、渠道新增日期明细与汇总。
- 日期汇总 ROIn = 成熟日期折算累计流水合计 / 同一批成熟日期安卓 App 消耗合计，不做每日 ROI 算术平均。

### ROI 成本

- 成本事件：`ta.v_event_41.roi_ad_platform`。
- 业务日期：`ge_date`；消耗：`ge_ad_cost`。
- 先按 `ge_date + ge_app_id + ge_ad_platform` 取最新 `#event_time` 快照，再汇总当日成本。
- 成本不按媒体、用户来源、行为渠道关联，仅按日期关联。
- `ge_app_id` 与 `channel_id` 是不同 ID 体系，不得混用。
- 已确认当前安卓 App / 引力 APPID：`25437280`；看板继续通过 `${Text:text4}` 筛选 APPID。
- 其他已知 APPID：`25048291`=抖音小游戏，`29756138`=微信小游戏。

### 成本日期完整性

ROI 主报表保留：

- `应有成本天数`
- `实际成本天数`
- `成本日期完整性`
- `缺失成本日期`

日期汇总成本完整性使用独立自然日历 + `roi_ad_platform` 成本集合判断，不依赖某个新增类型 / 媒体 / 端包当天是否存在 cohort。

日期汇总展示的“消耗”直接从当前 `${PartDate:date}` 日期范围的独立成本集合汇总，因此同一筛选日期范围下所有 `渠道新增日期=汇总` 行的消耗必须一致。

ROIn 的日期汇总成本分母只使用当前筛选范围内已经成熟到第 n 天的日期成本合计。
