# 下方了直播包及转端 LTV 口径

更新时间：2026-09-14

## 统计主体

- 统一以 `nb_open_id` 作为唯一玩家主体。
- 用户来源渠道 `active_channel`：同一 `nb_open_id` 在 `ta.v_user_41` 全量角色中，最早 `create_role_time` 对应的 `channel_id`。
- 行为渠道 `event_channel`：玩家实际 `in_out_log.channel_id`。
- 端包行为渠道池：`3056210 / 3056215 / 3056219`。
- `3056218` 主播直播体验包明确排除。

## 转端 / 端包分类

完全沿用当前跨渠道报表的分类逻辑：

1. `转端用户`：`active_channel = 3056211`（微信小游戏），后续实际进入端包行为渠道 `3056210 / 3056215 / 3056219`。
2. `端包用户`：`active_channel` 本身属于 `3056210 / 3056215 / 3056219`，且实际行为渠道也属于该端包池。

分类依据是“首次注册来源渠道 + 实际行为渠道”，不是比较不同角色的最早端包/微小创角时间，也不是用支付渠道反推用户类型。

## 渠道新增锚点

- 对每个 `nb_open_id × event_channel`，取该玩家第一次出现该端包行为渠道 `in_out_log` 的日期：`first_logindate_channel`。
- 该日期就是该玩家在该行为渠道的渠道新增日期，同时也是该渠道 LTV / 留存/ROI 的起点。
- 求 `first_logindate_channel` 时必须扫描完整历史起点（下方了当前可从 `2025-10-16` 起扫描），不能只在当前看板筛选日期内取最小值。
- 看板日期筛选应筛渠道新增日期，而不是限制后续 LTV / 留存 / ROI 事件扫描窗口。

## LTV

- LTV 按 `nb_open_id × event_channel` 统计。
- 支付事件：`ta.v_event_41.pay_log`。
- 有效支付：`payment > 0`，不限制 `pay_result`、`change_reason`。
- 金额单位：`payment / 100` 转元。
- 从 `first_logindate_channel` 当天开始，只统计同一 `nb_open_id` 且 `pay_log.channel_id = event_channel` 的支付；其他渠道支付不计入该行为渠道 LTV。
- 当前 LTV 输出扩展为 `LTV1~LTV180`；`LTVn` = 渠道新增日起第 1~n 个自然日的折算累计流水 / 渠道新增人数。
- `端包用户`流水按原值计入；`转端用户`流水统一乘 `0.4` 后计入 LTV；人数不乘 `0.4`。
- LTV 事件扫描必须覆盖渠道新增日起 180 天窗口，即支付 JOIN 最长扫描到 `渠道新增日期 + 179 天`。
- 每个 `LTVn` 单独判断成熟，成熟条件为 `渠道新增日期 + (n-1) <= 昨天`；未成熟返回 NULL。
- 媒体平台保留明细行，同时增加 `媒体平台=汇总` 行；媒体汇总发生在 `${Text:text3}` 媒体筛选之后。
- 新增类型保留 `转端用户 / 端包用户` 明细，同时增加 `新增类型=汇总` 行。该汇总在同一 `渠道新增日期 + event_channel` 下合并两类用户，分子为 `端包流水原值 + 转端流水×0.4`，分母为两类用户去重渠道新增人数原值。
- 因 `转端用户` 与 `端包用户` 的 `active_channel` 不同，`新增类型=汇总` 时 `用户来源ID` 同步输出 `汇总`，避免把跨来源汇总伪装成某个具体来源渠道。
- 同时保留 `新增类型=汇总 + 媒体平台明细` 与 `新增类型=汇总 + 媒体平台=汇总` 两层汇总。

## 留存

- 留存沿用与 LTV 完全相同的 cohort：`nb_open_id × event_channel`，渠道新增日期为 `first_logindate_channel`。
- 留存只认同一行为渠道的 `in_out_log`；同一 `nb_open_id` 在其他渠道活跃不计入当前行为渠道留存。
- D1 = 渠道新增当天，因此 D1 留存率理论上为 1；D2 = 渠道新增次日是否仍在同一 `event_channel` 存在 `in_out_log`，依此类推至 D30。
- 留存人数：对应 cohort 中在目标自然日于同一 `event_channel` 存在 `in_out_log` 的去重 `nb_open_id` 数。
- 留存率：目标日留存人数 / 渠道新增人数。
- 分母为对应 `渠道新增日期 + 用户来源ID + 行为渠道ID + 新增类型` 下的渠道新增去重 `nb_open_id` 数。
- 每个 Dn 单独判断成熟；观察截止统一为昨天，未成熟 Dn 返回 NULL。

## 媒体平台、汇总与 ROI

- 媒体平台取 `ta.v_user_41.ad_platform`，按同一 `nb_open_id` 最早 `create_role_time` 对应角色取值；NULL 或空字符串统一为 `natural`。
- 报表需要增加媒体平台维度，并支持 `${Text:text3}` 对归一化后的媒体平台筛选；同时增加“汇总”媒体行，汇总发生在媒体筛选之后。
- ROI 分子使用从渠道新增日起、同一 `event_channel` 的累计支付；`端包用户`按原值，`转端用户`累计支付乘 `0.4` 后参与 ROI。人数不乘 0.4。
- ROI 当前要求扩展到 `ROI1~ROI180`；`ROIn` = 渠道新增日起第 1~n 个自然日的折算累计流水 / 渠道新增日对应安卓 App 消耗。
- ROI 事件扫描必须覆盖渠道新增日起 180 天窗口，即支付 JOIN 最长扫描到 `渠道新增日期 + 179 天`；不得仍停留在 30 天窗口。
- 每个 `ROIn` 单独判断成熟，成熟条件为 `渠道新增日期 + (n-1) <= 昨天`；未成熟返回 NULL。
- 每日消耗读取 `ta.v_event_41` 的 `roi_ad_platform` 事件，业务日期使用 `ge_date`，消耗使用 `ge_ad_cost`。
- 消耗不按媒体平台、用户来源渠道、行为渠道关联；固定取“安卓 App”对应 APPID 的每日总消耗，仅按 `渠道新增日期 = ge_date` 关联。
- `roi_ad_platform` 是历史业务日期快照；应先按 `ge_date + ge_app_id + ge_ad_platform` 取最新 `#event_time`，再汇总 Android App 当日所有媒体消耗。
- **`ge_app_id` 与渠道表 `ta_ext.channel_id_41.channel_id` 不是同一字段体系。不得把 `3056210/3056219` 等 channel_id 当成 ROI 的 ge_app_id。** 当前已确认：`25048291`=抖音小游戏、`29756138`=微信小游戏；官方 Android App 的真实 `ge_app_id` 仍待确认。
- `ta_ext.channel_id_41` 仅用于渠道类型/名称映射。当前“官方Android渠道”包括 `3056222 / 3056210 / 3056221 / 3056218 / 3056219`，这不能反推出 ROI `ge_app_id`。
- 若 ROI 子查询用错误 APPID 过滤，会返回空集；外层 `coalesce(消耗,0)` 会把未关联到的 NULL 显示成 0，因此“消耗全为0”首先应检查 APPID 过滤和 `ge_date` 日期关联。
