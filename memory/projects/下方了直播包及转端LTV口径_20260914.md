# 下方了直播包及转端 LTV / ROI 口径

更新时间：2026-09-15

## 统计主体

- 统一以 `nb_open_id` 作为唯一玩家主体。
- 用户来源渠道 `active_channel`：同一 `nb_open_id` 在 `ta.v_user_41` 全量角色中，最早 `create_role_time` 对应的 `channel_id`。
- 行为渠道 `event_channel`：玩家实际 `in_out_log.channel_id`。
- 渠道新增日期：同一 `nb_open_id × event_channel` 第一次出现该行为渠道 `in_out_log` 的日期 `first_logindate_channel`。
- 首次渠道与首次进入渠道都必须先扫描完整历史，再应用看板日期筛选；当前历史起点使用 `2025-10-16`。

## 端包范围与筛选（2026-09-15 最新）

不再在 LTV / ROI 主看板中使用“微端包ID”参数 `${Text:text1}` 过滤，也不再使用“用户来源ID”参数 `${Text:text2}` 过滤。

端包集合统一动态读取：

```sql
SELECT DISTINCT cast(channel_id AS varchar)
FROM ta_ext.channel_id_41
WHERE channel_type IN ('官方Android渠道','官方Apple渠道')
```

即当前所有 `channel_type = 官方Android渠道 / 官方Apple渠道` 的包都自动进入统计，后续新增同类型渠道无需再改 SQL 的硬编码 ID 列表。

渠道名称同样从 `ta_ext.channel_id_41` 获取；JOIN 前按 `channel_id` 去重，避免渠道维表重复导致流水膨胀。

- 日看板、LTV、ROI 等输出 `微端包ID` 时同步展示 `微端包名称`；名称来源为 `ta_ext.channel_id_41.channel_name`。
- `微端包名称` 仅作为 `channel_id` 的展示属性，不改变统计粒度；关联前按 `channel_id` 去重，建议使用 `max(channel_name)` 保证一对一展示。

## 两种用户类型

只统计以下两类：

1. `转端用户`：`active_channel = 3056211`（微信小游戏），且实际进入上述动态端包集合中的某个 `event_channel`。
2. `端包用户`：`active_channel` 本身属于上述动态端包集合，且实际进入上述动态端包集合中的某个 `event_channel`。

报表恢复输出 `用户来源ID` 维度，但不增加用户来源筛选参数：

- 新增类型明细行：`用户来源ID = active_channel`。
- `新增类型=汇总` 行：`用户来源ID = 汇总`，避免跨来源汇总被误认为某个具体来源。
- 报表继续保留 `微端包ID / 微端包名称 + 新增类型 + 媒体平台` 等维度。

分类依据始终是“首次注册来源渠道 + 实际行为渠道”，不是比较不同角色的端包创角时间，也不是用支付渠道反推用户类型。

## 媒体平台

- 媒体平台取 `ta.v_user_41.ad_platform`，按同一 `nb_open_id` 最早 `create_role_time` 对应角色取值。
- NULL / 空字符串统一为 `natural`。
- 保留 `${Text:text3}` 媒体平台筛选。
- 保留媒体明细行和 `媒体平台=汇总` 行，媒体汇总发生在媒体筛选之后。

## LTV

- 按 `nb_open_id × event_channel` 统计。
- 支付事件：`ta.v_event_41.pay_log`。
- 有效支付：`payment > 0`，不限制 `pay_result`、`change_reason`。
- 金额单位：`payment / 100` 转元。
- 从渠道新增日起，只统计同一 `nb_open_id` 且 `pay_log.channel_id = event_channel` 的支付。
- 支付渠道也必须属于上述动态端包集合。
- `端包用户`流水原值；`转端用户`流水乘 `0.4`；人数不打折。
- 输出 `LTV1~LTV180`；`LTVn` = 渠道新增日起第 1~n 个自然日折算累计流水 / 渠道新增人数。
- 支付最长扫描到 `渠道新增日期 + 179 天`。
- 每个 `LTVn` 单独成熟：`渠道新增日期 + (n-1) <= 昨天`，未成熟返回 NULL。
- 保留 `用户来源ID`、`新增类型=端包用户 / 转端用户 / 汇总`、媒体平台等维度。
- 新增类型明细行按实际 `active_channel` 展示用户来源；新增类型汇总行 `用户来源ID=汇总`。
- 新增类型汇总分子 = 端包流水原值 + 转端流水×0.4；分母 = 两类新增人数原值。
- 保留 `渠道新增日期=汇总` 行；日期汇总 LTV 不做每日 LTV 算术平均，而按成熟 cohort 的 `折算累计流水合计 / 成熟新增人数合计` 计算。

## 留存

- cohort 与 LTV 一致：`nb_open_id × event_channel`。
- 留存只认同一 `event_channel` 的 `in_out_log`。
- D1 = 渠道新增当天；Dn = 渠道新增后第 n 个自然日。
- 每个 Dn 单独判断成熟；未成熟返回 NULL。

## ROI

- ROI 分子与 LTV 流水一致：同一 `nb_open_id × event_channel` 累计支付，端包原值、转端×0.4。
- 输出 `ROI1~ROI180`，支付最长扫描到 `+179天`。
- 每个 ROIn 单独成熟；未成熟返回 NULL。
- 若某个日期汇总维度在 ROIn 下没有任何成熟 cohort，则该 ROIn 返回 NULL，不显示伪 0%。
- 保留 `用户来源ID`、新增类型明细与汇总、媒体明细与汇总、渠道新增日期明细与汇总。
- 新增类型明细行按实际 `active_channel` 展示用户来源；新增类型汇总行 `用户来源ID=汇总`。
- 日期汇总 ROIn = 成熟日期折算累计流水合计 / 对应微端包 `gravity_app_id` 映射后的同一批成熟日期消耗合计，不做每日 ROI 算术平均。

### ROI 成本（2026-09-15 最新）

- 成本事件：`ta.v_event_41.roi_ad_platform`。
- 业务日期：`ge_date`；消耗：`ge_ad_cost`。
- 先按 `ge_date + ge_app_id + ge_ad_platform` 取最新 `#event_time` 快照，再汇总 `日期 × ge_app_id` 成本。
- 微端包成本关联不再使用固定 APPID 参数 `${Text:text4}`。
- 每个 `event_channel / 微端包ID` 先通过 `ta_ext.channel_id_41.channel_id` 找到该包的 `gravity_app_id`，再用标准化后的 `gravity_app_id = roi_ad_platform.ge_app_id` 关联对应 App 成本。
- 完整链路：`微端包ID(channel_id) -> ta_ext.channel_id_41.gravity_app_id -> roi_ad_platform.ge_app_id -> ge_ad_cost`。
- `ge_app_id` 与 `channel_id` 是不同 ID 体系，不得直接相等关联。
- 成本不按 `用户来源ID / 新增类型 / 媒体平台` 分摊；同一微端包下这些维度共享该微端包对应 App 的同日成本。
- 若多个微端包的 `gravity_app_id` 相同，则这些微端包会共享同一份 App 级成本；这是当前成本源粒度决定的，不能将其简单跨微端包求和作为总成本。
- 已观察到部分当前渠道的 `gravity_app_id` 为 `25437280`，但主报表不再硬编码该值，统一动态读取渠道维表。

### 成本日期完整性

ROI 主报表保留：

- `应有成本天数`
- `实际成本天数`
- `成本日期完整性`
- `缺失成本日期`

日期汇总成本完整性使用独立自然日历 + 微端包 `gravity_app_id` 对应的 `roi_ad_platform` 成本集合判断，不依赖某个用户来源 / 新增类型 / 媒体当天是否存在 cohort。

日期汇总展示的“消耗”为当前 `${PartDate:date}` 日期范围内、该 `微端包ID -> gravity_app_id -> ge_app_id` 对应成本合计；因此同一微端包下所有用户来源 / 新增类型 / 媒体维度的日期汇总消耗应一致。不同微端包若 `gravity_app_id` 不同，消耗可以不同；若 `gravity_app_id` 相同，则消耗应一致。

ROIn 的日期汇总成本分母只使用当前筛选范围内已经成熟到第 n 天、且属于该微端包映射 App 的日期成本合计。


## 付费留存报表（2026-09-18）

- 报表格式沿用当前渠道 LTV 报表：`渠道新增日期 / 用户来源ID / 微端包ID / 微端包名称 / 新增类型 / 媒体平台`，并保留 `渠道新增日期=汇总` 行。
- cohort 与 LTV 一致：同一 `nb_open_id × event_channel` 第一次进入端包的日期为渠道新增日期。
- 端包范围继续动态读取 `ta_ext.channel_id_41` 中 `channel_type IN ('官方Android渠道','官方Apple渠道')`。
- 《下方了》付费留存统一定义为：`D1付费用户中，第N日仍有登录/活跃的人数 / D1付费人数`，后续第N日不要求再次付费。
- D1付费用户：渠道新增当天、同一 `event_channel` 存在有效 `pay_log(payment>0)` 的玩家。
- 第N日留存：上述 D1付费用户在渠道新增后的第N个自然日、同一 `event_channel` 存在 `in_out_log` 即算留存。
- 输出 `D1付费人数` 与 `付费留存1~付费留存180`；`付费留存1` 在 D1 有付费人数时应为 1。
- 每个 `付费留存N` 单独判断成熟：`渠道新增日期 + (N-1) <= 昨天`；未成熟返回 NULL。
- 日期汇总的 `付费留存N` 不做每日留存率算术平均，而按成熟 cohort 的 `第N日留存人数合计 / 同批成熟 cohort 的 D1付费人数合计` 计算。
- 付费留存为人数指标，不做转端 `×0.4` 折算。

- 2026-09-24 ROI广告看板 APPID 映射调整：不再在 SQL 中硬编码 ge_app_id -> channel_id / 包体名称。
- 统一通过 ta_ext.channel_id_41 关联：标准化 roi_ad_platform.ge_app_id 与 channel_id_41.gravity_app_id 后匹配，输出 channel_id、channel_name（作为包体）和 channel_type。
- 标准化建议：try_cast(trim(cast(ge_app_id as varchar)) as double) -> bigint；gravity_app_id 同样标准化后关联。

- 2026-09-24 `roi_operator` 看板同样改为配置表映射：`ge_app_id -> ta_ext.channel_id_41.gravity_app_id -> channel_id/channel_name/channel_type`，不再硬编码 APPID。
- `roi_operator` 最新快照粒度继续保留 `ge_date + ge_app_id + ge_ad_platform + ge_operator`。

- 2026-09-24 一对多映射风险：若同一个 gravity_app_id 在 ta_ext.channel_id_41 对应多个 channel_id/channel_name，直接按 ge_app_id=gravity_app_id LEFT JOIN 会复制同一条 ROI 源记录；且当前使用 rank() 按 ge_date+ge_app_id+ge_ad_platform(+ge_operator) 排最新时，这些复制行 #event_time 完全相同，会同时得到 rank=1，因此 WHERE paixu=1 仍无法去重，后续汇总会按映射行数成倍放大。
- 修复原则：ROI 源数据粒度是 APPID 时，channel_id_41 必须先按 gravity_app_id 聚成一行再关联；可输出 channel_id/channel_name 列表用于展示，但不得把同一份 APPID 成本重复分摊到多个 channel_id 后再求和。若业务必须分包体，则需要更细粒度的成本源或明确分摊规则。

- 2026-09-24 特殊 APPID 映射：当 gravity_app_id / ge_app_id = 25437280 时，ROI 看板映射到 ta_ext.channel_id_41 时仅保留 channel_name='官方Android渠道'，避免该 APPID 一对多映射导致 ROI 数据复制。其他 APPID 暂按原配置映射。
