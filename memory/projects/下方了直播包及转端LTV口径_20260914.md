# 下方了直播包及转端 LTV 口径

更新时间：2026-09-15

## 统计主体

- 统一以 `nb_open_id` 作为唯一玩家主体。
- 用户来源渠道 `active_channel`：同一 `nb_open_id` 在 `ta.v_user_41` 全量角色中，最早 `create_role_time` 对应的 `channel_id`。
- 行为渠道 `event_channel`：玩家实际 `in_out_log.channel_id`。
- 当前端包行为渠道池：`3056210 / 3056215 / 3056218 / 3056219 / 3056221 / 3056222`。
- `3056218 / 3056221 / 3056222` 不再排除；`3056214` 抖音小游戏、`3056220` 支付宝小游戏仍不进入这套微信转端分类。

## 转端 / 端包分类

1. `转端用户`：`active_channel = 3056211`（微信小游戏），后续实际进入端包行为渠道 `3056210 / 3056215 / 3056218 / 3056219 / 3056221 / 3056222`。
2. `端包用户`：`active_channel` 本身属于 `3056210 / 3056215 / 3056218 / 3056219 / 3056221 / 3056222`，且实际行为渠道也属于该端包池。

分类依据是“首次注册来源渠道 + 实际行为渠道”，不是比较不同角色的最早端包/微小创角时间，也不是用支付渠道反推用户类型。

## 渠道新增锚点

- 对每个 `nb_open_id × event_channel`，取该玩家第一次出现该端包行为渠道 `in_out_log` 的日期：`first_logindate_channel`。
- 该日期就是该玩家在该行为渠道的渠道新增日期，同时也是该渠道 LTV / 留存 / ROI 的起点。
- 求 `first_logindate_channel` 时必须扫描完整历史起点（下方了当前可从 `2025-10-16` 起扫描），不能只在当前看板筛选日期内取最小值。
- 看板日期筛选应筛渠道新增日期，而不是限制后续 LTV / 留存 / ROI 事件扫描窗口。

## LTV

- LTV 按 `nb_open_id × event_channel` 统计。
- 支付事件：`ta.v_event_41.pay_log`。
- 有效支付：`payment > 0`，不限制 `pay_result`、`change_reason`。
- 金额单位：`payment / 100` 转元。
- 从 `first_logindate_channel` 当天开始，只统计同一 `nb_open_id` 且 `pay_log.channel_id = event_channel` 的支付；其他渠道支付不计入该行为渠道 LTV。
- 当前 LTV 输出 `LTV1~LTV180`；`LTVn` = 渠道新增日起第 1~n 个自然日的折算累计流水 / 渠道新增人数。
- `端包用户`流水按原值计入；`转端用户`流水统一乘 `0.4` 后计入 LTV；人数不乘 `0.4`。
- LTV 事件扫描必须覆盖渠道新增日起 180 天窗口，即支付 JOIN 最长扫描到 `渠道新增日期 + 179 天`。
- 每个 `LTVn` 单独判断成熟，成熟条件为 `渠道新增日期 + (n-1) <= 昨天`；未成熟返回 NULL。
- 媒体平台保留明细行，同时增加 `媒体平台=汇总` 行；媒体汇总发生在 `${Text:text3}` 媒体筛选之后。
- 新增类型保留 `转端用户 / 端包用户` 明细，同时增加 `新增类型=汇总` 行。该汇总在同一 `渠道新增日期 + event_channel` 下合并两类用户，分子为 `端包流水原值 + 转端流水×0.4`，分母为两类用户去重渠道新增人数原值。
- 因 `转端用户` 与 `端包用户` 的 `active_channel` 不同，`新增类型=汇总` 时 `用户来源ID` 同步输出 `汇总`。
- LTV 报表保留 `渠道新增日期=汇总` 行；日期汇总的 `LTVn` 按成熟 cohort 的折算累计流水合计 / 同一批成熟 cohort 新增人数合计计算，不做每日 LTV 算术平均。

## 留存

- 留存沿用与 LTV 完全相同的 cohort：`nb_open_id × event_channel`，渠道新增日期为 `first_logindate_channel`。
- 留存只认同一行为渠道的 `in_out_log`；同一 `nb_open_id` 在其他渠道活跃不计入当前行为渠道留存。
- D1 = 渠道新增当天；D2 = 渠道新增次日是否仍在同一 `event_channel` 存在 `in_out_log`，依此类推。
- 留存人数：对应 cohort 中在目标自然日于同一 `event_channel` 存在 `in_out_log` 的去重 `nb_open_id` 数。
- 留存率：目标日留存人数 / 渠道新增人数。
- 每个 Dn 单独判断成熟；观察截止统一为昨天，未成熟 Dn 返回 NULL。

## 媒体平台、汇总与 ROI

- 媒体平台取 `ta.v_user_41.ad_platform`，按同一 `nb_open_id` 最早 `create_role_time` 对应角色取值；NULL 或空字符串统一为 `natural`。
- ROI 分子使用从渠道新增日起、同一 `event_channel` 的累计支付；`端包用户`按原值，`转端用户`累计支付乘 `0.4` 后参与 ROI。人数不乘 0.4。
- ROI 输出 `ROI1~ROI180`；`ROIn` = 渠道新增日起第 1~n 个自然日的折算累计流水 / 渠道新增日对应安卓 App 消耗。
- ROI 支付扫描最长到 `渠道新增日期 + 179 天`；每个 `ROIn` 单独判断成熟，成熟条件为 `渠道新增日期 + (n-1) <= 昨天`。
- 新增类型增加 `汇总` 行：同一 `渠道新增日期 + event_channel` 下合并 `端包用户 + 转端用户`；ROI 分子为 `端包流水原值 + 转端流水×0.4`，成本不重复相加。
- `新增类型=汇总` 时 `用户来源ID=汇总`；同时保留媒体明细与媒体汇总。
- ROI 报表增加 `渠道新增日期=汇总` 行。日期汇总 ROIn 不允许对每日 ROI 做算术平均，而是使用 `成熟日期折算累计流水合计 / 同一批成熟日期安卓 App 消耗合计`。
- 若某个日期汇总维度在 ROIn 下没有任何成熟 cohort，则该 ROIn 返回 NULL，不允许显示伪 0%。

### ROI 成本

- 每日消耗读取 `ta.v_event_41.roi_ad_platform`；业务日期 `ge_date`，消耗 `ge_ad_cost`。
- 消耗不按媒体平台、用户来源渠道、行为渠道关联；仅按日期关联。
- `roi_ad_platform` 为历史业务日期快照：先按 `ge_date + ge_app_id + ge_ad_platform` 取最新 `#event_time`，再汇总当日各媒体消耗。
- `ge_app_id` 与 `ta_ext.channel_id_41.channel_id` 是不同 ID 体系，不得混用。
- 已确认当前安卓 App / 引力 APPID：`25437280`。
- 其他已知 APPID：`25048291`=抖音小游戏，`29756138`=微信小游戏。
- 当前看板可继续通过 `${Text:text4}` 筛选 APPID，但标准值应使用 `25437280`。

### 成本日期完整性校验

ROI 主报表增加以下字段：

- `应有成本天数`：`${PartDate:date}` 当前筛选日期范围内理论应存在成本的自然日数量。
- `实际成本天数`：同一日期范围内实际在 `roi_ad_platform` 查到成本的日期数量。
- `成本日期完整性`：实际成本天数 = 应有成本天数则为 `完整`，否则为 `缺失`。
- `缺失成本日期`：列出当前筛选日期范围内未查到成本的具体日期。

日期汇总的成本完整性必须基于独立自然日历 + `roi_ad_platform` 成本集合判断，不能依赖某个用户来源 / 新增类型 / 媒体当天是否存在 cohort。

日期汇总展示的 `消耗` 直接从当前筛选日期范围的独立成本集合汇总，因此同一日期筛选范围下所有 `渠道新增日期=汇总` 维度行的消耗必须一致。

ROIn 日期汇总成本分母同样来自独立成本集合，只使用当前筛选日期范围内已经成熟到第 n 天的日期成本合计，不因某个业务维度某天没有 cohort 而少算成本。
