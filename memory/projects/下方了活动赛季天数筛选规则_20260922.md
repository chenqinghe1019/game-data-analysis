# 下方了活动分析：赛季开启天数筛选规则（2026-09-22）

- 项目：下方了（v_event_41）
- 新增筛选参数：赛季，默认用 `${Selector:selector3}`。
- 原活动活跃限制从“开服天数区间”改为“所选赛季开启天数区间”。
- `${Selector:selector2}` 继续表示区间表达式，例如 `between 1 and 7`，但语义改为赛季第N天。
- 赛季开启日定义：同一 `region_id + season` 下，`in_out_log` 首次出现该赛季的日期。
- 活动开始/结束时间也改为基于赛季开启日推导：
  - 活动开始时间 = 赛季开启日 + (区间开始天数 - 1)
  - 活动结束时间（右开） = 赛季开启日 + 区间结束天数
- 成熟判断仍保留：完整赛季天数区间必须全部落在 `${PartDate:date2}` 统计周期内。
- 活跃玩家必须在所选赛季、对应赛季天数区间内存在 `in_out_log`。
- VIP仍取活动开始时间之前的历史最大 `vip_change_log.after`。
- 活动参与/活动付费事件仍限制在活动开始时间至活动结束时间内。
- 商品映射继续使用 `ta_ext.product_id_name_41`，按 `product_id + product_name` 双字段关联。

- Selector边界解析规则：`${Selector:selector2}`是条件表达式，不能再用regexp_extract当字符串拆解。为保留完整体验/成熟周期判断，使用`unnest(sequence(1, 1000))`生成天数序列，再通过`WHERE day_num ${Selector:selector2}`筛选，取`min(day_num)`和`max(day_num)`作为活动开始/结束天数。
- 该改法只替换Selector边界获取方式，不改变原有成熟判断、活动活跃、参与、付费、VIP截止等业务逻辑。

- selector3_input_example: 赛季Selector为条件表达式，填写 `= 1`、`in (1,2)`，SQL使用 `try_cast(season AS bigint) ${Selector:selector3}`；不要填写裸值 `1`、`S1` 或 `1赛季`。
- selector2_input_example: 赛季开启天数建议使用连续区间，例如 `between 1 and 6`；SQL通过sequence生成天数后直接套用Selector条件并取min/max做完整体验判断。
