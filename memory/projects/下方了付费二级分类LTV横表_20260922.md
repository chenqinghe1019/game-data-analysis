# 下方了付费二级分类LTV横表口径（2026-09-22）

- 基于 sql/xiafangle_payment_item_ltv_contribution_d1_d30_v41.sql 优化。
- 新增天数改用 `${Number:number6}` 条件型参数筛选，写法为 `(days + 1) ${Number:number6}`。
- 输出由“新增第N天纵向行”改为 D1-D30 横向列。
- 不再按具体商品、product_id、product_name、配置单价、一级分类分组。
- 仅按 `product_type_two`（二级分类/付费小类）汇总。
- 每个新增日期增加“汇总”行，汇总所有二级分类。
- 横表 D1-D30 默认表示“累计LTV贡献”；二级分类行=该二级分类累计付费金额/该新增日新增人数；汇总行=累计总LTV。
- 支付金额口径保持原逻辑：payment非0优先payment，否则token_payment，最后/100转元；直充剔除规则保持不变（直充中商品名含“钻石”仍保留）。
- 商品映射继续使用 ta_ext.product_id_name_41，并按 product_id + product_name 双字段关联。

- 口径调整（2026-09-22）：新增日期只作为 `${PartDate:date}` 的筛选范围，不再作为结果分组维度。
- 跨所选新增日期汇总后，仅按 `product_type_two` 输出，并保留“汇总”行。
- 每个 Dn 的分母必须使用“所选新增日期中已经成熟到 Dn 的新增玩家数”，因此跨新增日期汇总后不同 Dn 的成熟新增人数可能不同，不能使用一个统一新增人数作为全部 Dn 分母。

- 含未成熟版本调整（2026-09-22）：针对原 SQL 中 `target_date <= current_date` 的版本，同样改为“新增日期仅筛选、二级分类汇总、D1-D30 横表、汇总行、Number新增天数筛选”。
- 含未成熟版本保留原逻辑：允许 `target_date = current_date`，即当天尚未完整结束的数据也纳入对应 Dn；因此该版本每个 Dn 分母为所选新增日期中“截至当前已到达该 Dn（含今天）”的新增玩家数。
- 横表后不再单独输出“成熟状态”，因为同一个 Dn 跨多个新增日期汇总时可能同时包含成熟批次与当天未成熟批次。

- product_name 明细版本（2026-09-22）：在同一成熟LTV横表口径下，新增一个具体到 `product_name` 的版本；结果按 `product_type_two + product_name` 分组，并保留“汇总”行。
- product_name 明细版本同样保留 `${PartDate:date}` 新增日期筛选、`${Number:number6}` 新增天数筛选和媒体筛选 `coalesce(ad_platform,'自然量') ${Text:text}`。
- product_name 明细版本仍以“截至 Dn 累计付费金额 / 已成熟到 Dn 的新增人数”作为 Dn 的LTV贡献。

- 2026-09-23 输出调整：横表需要显式展示每个 Dn 对应的成熟新增人数，建议与 LTV 列成对输出，如 `D1新增人数, D1, D2新增人数, D2...`。
- 由于跨新增日期汇总后不同 Dn 的成熟样本不同，不能只放一个统一“新增人数”列；每个 Dn 的新增人数即该 Dn LTV 的实际分母。
