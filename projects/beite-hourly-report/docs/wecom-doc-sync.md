状态：2026-11-21已启用。目标：[分时数据维度](https://doc.weixin.qq.com/sheet/e3_ATAAJgZqAKwCNWmMVbVfXSPOCDHxH?tab=3w1bzn)。仅更新该子表，其他三个sheet不改。

## 用户确认的执行规则

- 以正式企微推送为口径，来源是联合小时报SQLite，直接复用生产行生成函数 `externalRowValues`，不重拉实时数冒充旧小时。
- 每天11点起（含11点）补数；00点执行属于前一天24点，可补。1–10点不补，不改变原小时报推送时段。
- 日期与小时对应到既有行，只补缺失，不插入、不移动行，不清空原数据，不改辅助列和顶部汇总区。
- 2026-11-23新增例外：同步时刷新北京时间前一天24点行的付费次留、注册次留（Y/Z），取正式推送存档中的最新留存；允许更新已有留存数值，来源缺失不覆盖，已有公式仍保护。午夜刚生成的24点收盘行不刷新留存，待后续播报再更新。写前核对原单元格未改变，写后回读验证。
- 除上述留存刷新外，已有数字（包括0）保留；空单元格、空字符串和横线占位符可补，来源缺失不编造。已有公式保留，即使其计算值暂为空。
- 核对第18行表头，数据从第20行E:Z写入。辅助时间A与日期C/小时D须能一致定位；重复主键、非整点、日期不一致或缺少预置行时不猜位置。
- 格式以第98行按列复制：字体、颜色、对齐、数字格式；R/S成本列对齐98行的两位小数显示，保留底层原值。日期合并和边框不改变。

## 实现

`run.mjs`在截图和文字均已确认成功后调用 `wecom-doc-sync.mjs`，也覆盖「截图已成功、本次仅补文字」分支。仅external项目启用此可选配置；其他播报不受影响。

Node只排队并隐藏启动独立Python进程。Python启动Node取数和文档工具时同样使用Windows无控制台模式，避免弹出黑框。Python通过已授权的官方WeCom CLI读写，不操作浏览器、不读取Cookie、不接管用户桌面。`wecom-doc-source.mjs`只读正式存档，复用与XLSX完全相同的值生成逻辑。

本机配置：`%LOCALAPPDATA%/GravityWeComReport/external/wecom-doc-sync.json`。关键字段：enabled、docid、sheet、minimumHour=11、formatReferenceRow=98、archive（必须是当前配置目录里的正式hourly-snapshots.sqlite）。配置和CLI授权留本机。

状态、待处理请求、日志和互斥锁：同目录的 `wecom-doc-sync/`。status.json可区分已完成和pending；请求失败不改变已成功群播报，不重发图片或文字。网络结果不明时下一轮先重读，临时失败最多3次；权限/参数错误停止，后续成功推送会再次扫描补缺。工作进程设15分钟预算，锁过期30分钟，防止并行写入。

同一任务按固定矩形分批，每批不超过400格。写前重新检查行键与缺失状态，写后逐值回读；表有新内容时停止避免覆盖。不支持跨请求事务，外部人工并发编辑可能使任务停止；下次只补剩余空缺。

CLI把已存储的空字符串也判为占用，allow_overwrite=false会报640027。对这种已读确认的空值/占位符使用受检查的覆盖写入；并不授权覆盖已有数值。格式随新值一并写入，手工修复现有格式使用style接口，不重写数据。

## 历史限制

旧外部企业文档经能力审批后仍报640008；新内部文档已经实测可读写。不能再将旧文档的限制描述成当前内部文档也不可用。早期浏览器受限时未用CDP/Cookie等途径绕过；当前使用用户单独授权的 [WecomTeam/wecom-cli](https://github.com/WecomTeam/wecom-cli)。

在线表已有部分成本/ROI公式属于旧口径；本轮按用户“只补缺失”要求保留它们，不将整个在线表宣称为已按当前口径全部重算。补入字段来自当前正式播报，既有值若需重算，应另明确范围。
