# 游戏数据分析问题与解决经验

本文记录项目分析中反复出现、容易导致错误结论的问题。它沉淀的是可复用的排查方法，不是某次测试的结论或临时业务数值。

## 1. 指标口径与样本

### 1.1 把当日值和累计值混在一起
- **表现**：D1、D7、D30 指标看起来不一致，或把第 N 天金额当成累计金额。
- **原因**：没有先确认指标是目标自然日当天，还是 cohort 起点到目标日的累计值。
- **解决**：先按 Canonical 指标字典锁定定义；表头直接标“第 N 天”或“累计 N 天”；分日与累计指标分开计算和展示。

### 1.2 用未成熟 cohort 计算完整周期指标
- **表现**：近期新增 cohort 的 D7/D30、LTV 或活动周期值明显偏低。
- **原因**：观察窗口尚未结束，却被当成完整样本。
- **解决**：按每个目标观察日判断成熟度；不成熟样本单列或排除，不用部分累计值冒充完整 DN 指标。若用户明确要求统一 cohort，再按最大观察天数统一样本。

### 1.3 把付费留存当成再次付费
- **表现**：后续登录过的基准付费玩家被漏掉，或留存率与复购率混在一起。
- **原因**：把“后续活跃”错误地要求成“后续再次付费”。
- **解决**：默认付费留存 = 基准日付费 cohort 在目标日再次登录/活跃人数 ÷ 基准日付费人数；再次付费另命名为复购率。

### 1.4 首日付费分层误用累计付费
- **表现**：首日付费档人数与玩家首日实际付费行为不符。
- **原因**：直接使用历史累充、查询区间累计金额或当前累计付费字段。
- **解决**：先汇总注册/创角当天真实有效支付，再做首日 R 档；累计 R 档另算，不能互相替代。

### 1.5 分组率的简单平均造成总体指标错误
- **表现**：整体留存率、付费率或 LTV 与分组数据汇总后对不上。
- **原因**：直接平均各渠道、服务器或付费层的比例/人均值。
- **解决**：总体率 = 总分子 / 总分母；总体 ARPU/LTV = 总金额 / 对应总人数。只有权重完全相同时，简单平均才可能等价。

### 1.6 LTV 贡献与活动流水贡献混淆
- **表现**：活动金额为 0，但报表仍显示 LTV 贡献；或活动金额和贡献值方向不一致。
- **原因**：贡献指标可能用了 cohort 全量流水、不同观察窗口或不同分母，而活动金额只统计活动订单。
- **解决**：先写出贡献公式，确认收入范围、cohort、观察窗口和分母；分别输出活动流水、全量 LTV 和活动流水占比，不要把它们都叫“活动 LTV 贡献”。

## 2. 人群、身份和去重

### 2.1 账号、角色、跨渠道玩家和设备混用
- **表现**：玩家数重复、跨服/跨端人数不合理，或者同一玩家被统计多次。
- **原因**：不同表的身份粒度不同；角色数不等于账号数，账号数也不一定等于跨渠道玩家数。
- **解决**：先声明分析粒度并按项目 FACTS 选键。下方了跨渠道分析使用 nb_open_id；角色分析使用角色键；历史标签按 #user_id 关联。不要默认用 open_id 替代 nb_open_id。

### 2.2 一对多 JOIN 导致人数或流水膨胀
- **表现**：JOIN 后人数翻倍、流水变大、转化率超过 100%。
- **原因**：标签、渠道映射、商品维表、角色明细或事件明细在关联键上不唯一。
- **解决**：JOIN 前先检查每个键的匹配条数；将维表压缩到唯一映射或先聚合事实表；JOIN 后复核总人数和总金额是否守恒。

### 2.3 事件次数被当成人数
- **表现**：进入关卡人数、战斗人数或参与人数偏大。
- **原因**：同一玩家可重复触发事件或多次挑战。
- **解决**：先定义玩家粒度和业务键，再按玩家/关卡、账号/battle_uid 等去重。次数指标和人数指标分开命名。

## 3. 关卡、肉鸽和漏斗

### 3.1 0 次肉鸽玩家被漏掉
- **表现**：0 次肉鸽人数不合理，甚至与进入关卡人数完全相同或完全缺失。
- **原因**：只从肉鸽触发事件统计，未触发肉鸽事件的玩家没有记录，因而从结果集中消失；也可能把关卡进入人数误当成 0 次人数。
- **解决**：
  1. 先构建进入对应关卡的玩家全集。
  2. 按玩家和关卡选取用户要求的战斗记录（例如该玩家该关卡末次 battle_uid）。
  3. 聚合该场战斗的肉鸽次数。
  4. 将行为聚合 LEFT JOIN 回关卡玩家全集，缺失次数按业务定义补 0。
  5. 检查所有肉鸽次数分桶人数之和是否等于进入关卡人数。
- **关键点**：0 次人数是“进入关卡且末次战斗肉鸽次数为 0”的玩家数；不是不加条件地复制进入关卡人数。

### 3.2 关卡上一节点人数重复
- **表现**：上一节点/进入关卡人数出现重复，下一节点转化率失真。
- **原因**：以事件行或战斗次数作为玩家数，或把多次挑战的同一玩家重复计入。
- **解决**：每个玩家每个关卡只保留一个统计身份；如果分析挑战过程，再单独增加挑战序号维度。上一节点人数用去重玩家集合，下一节点人数用该集合中实际到达下一关的去重玩家。

### 3.3 末次挑战和累计挑战混淆
- **表现**：玩家对应关卡的肉鸽次数、失败次数或通关状态不符合预期。
- **原因**：把该玩家在该关卡的所有 battle_uid 累计，误当成末次战斗表现。
- **解决**：先按玩家 + 关卡分组，依据实际战斗开始/结束时间选最后一场 battle_uid；只有确认 battle_uid 是可靠时间序列时才用它排序。随后只统计这场战斗的数据。

### 3.4 失败、重试和流失没有拆开
- **表现**：失败人数无法解释后续流失，重复挑战比例和直接退出比例混淆。
- **原因**：只看失败事件，没有追踪失败后是否再次挑战、是否进入下一关。
- **解决**：以失败玩家为全集，分别统计失败后重试、失败后通关、失败后未再进入/直接流失；同时给出占失败人数和占挑战人数的比例。注明观察截止时间，避免把尚未观察完的玩家判为流失。

## 4. 战斗伤害、VIP 与异常值

### 4.1 把单角色伤害当成整场伤害
- **表现**：整场伤害与战斗汇总不一致。
- **原因**：battle_array 等结构中包含多个角色/单位，查询却只按某一个 role_id 统计。
- **解决**：用户问整场伤害时解析并汇总该场战斗所有角色/单位的伤害，再按 battle_uid 汇总；只有明确问角色伤害时才按角色拆分。城墙受击伤害、角色输出伤害和战斗总伤害必须分开。

### 4.2 用当前 VIP 代替战斗时 VIP
- **表现**：历史战斗按 VIP 拆分后结果不可信。
- **原因**：玩家 VIP 会变化，当前 VIP 不能代表历史战斗时等级。
- **解决**：按战斗时间匹配 history_tag 的历史 VIP 快照；用户级标签使用 #user_id -> #long_id。已确认的场景中没有 VIP 历史记录按 VIP0 处理，并在输出口径中说明。

### 4.3 最大值或分位数被异常样本误导
- **表现**：P99 或最大伤害远超常态，难以定位。
- **原因**：没有先确认样本粒度、重复记录、无效战斗、字段类型和分组。
- **解决**：先核对战斗唯一键、总伤害聚合、有效样本；同时输出 P50、P75、P99、最大值，并按关卡/VIP/付费档拆分。对最大值回查原始战斗明细，不只报告一个异常数字。

## 5. 活动、礼包与资源

### 5.1 页面打开被误判为活动参与
- **表现**：参与人数明显偏大，或参与率与实际资源行为不符。
- **原因**：用打开页面、进入活动或登录事件代替真实参与行为。
- **解决**：先确认参与的业务定义。若定义为指定道具消耗，按道具 ID 和真实消耗日志统计；必要时同时核对 item_log 与 money_log。页面曝光、购买、领取、消耗分开统计。

### 5.2 购买与领取奖励的条件混淆
- **表现**：把购买战令的人误认为已领取奖励，或仅凭奖励事件认定已购买。
- **原因**：购买行为和奖励领取/获得是两个不同条件。
- **解决**：按玩家分别构建购买集合和指定奖励获得集合，再按需求做交集；奖励 ID 与数量均需核验。若只要求购买用户，不额外要求领取奖励。

### 5.3 商品或道具映射缺失
- **表现**：出现“未命名礼包”、活动金额缺失或道具被归入错误分类。
- **原因**：埋点字段不一定线上实际存在，或商品维表未覆盖新 ID。
- **解决**：先检查线上事件原始值和维表未匹配项；明确使用 product_id、product_name 或 item_id 的优先级。不要假设需求文档字段已实际入库。

## 6. 合服、版本与分组比较

### 6.1 合服窗口漏掉合服周
- **表现**：合服前后 LTV 或活跃对比与实际过程相悖。
- **原因**：只比较合服前一周和后一周，遗漏合服当天所在周的波动。
- **解决**：按“合服前一周 → 合服周 → 合服后一周”列出三段；合服周是否包含合服日按统一规则明确。按合并 cohort 总流水/总人数计算加权 LTV，不平均各服 LTV。

### 6.2 把合服日期分析又按区服拆散
- **表现**：结果表中出现大量 zone_id 分组，无法直接比较合服批次。
- **原因**：沿用旧 SQL 的服务器分组，没有按本次需求改成合服日期分组。
- **解决**：当用户要求按合服日期分组时，只用合服日期作为分组键；合服前/周/后作为指标列或对比区间，不额外当分组项。

### 6.3 版本对比的日期和人群不一致
- **表现**：不同测试版本指标看似有明显差异，但无法确认是否来自版本本身。
- **原因**：日期范围、渠道结构、平台、付费分层、成熟样本或首日定义不同。
- **解决**：先统一样本条件，再比较总体和分层；对启动、首次战斗、引导、关卡等链路逐节点定位。只有证据支持时才归因到具体流程或功能。

## 7. 埋点与数据源核验

### 7.1 埋点文档有字段，线上数据却为空
- **表现**：SQL 使用文档字段但结果为空，或字段不存在。
- **原因**：埋点方案、已取消字段和线上实际入库字段不一致。
- **解决**：黄色标记、删除线或明确取消的事件/属性不纳入有效埋点；先查线上表结构和小范围真实事件样本。文档字段只有经过线上核验后才能作为已确认数据源。

### 7.2 新增、活跃和在线时长使用同一个事件
- **表现**：活跃人数有数据，但在线时长缺失或人均时长偏差。
- **原因**：活跃事件与时长上报事件可能不同；某些项目只在会话结束时上报时长。
- **解决**：按项目 FACTS 分别确定活跃事件和时长事件；没有时长记录的活跃玩家仍应保留在人均时长分母中，并单独展示时长覆盖率。

## 8. 数据文件与报告交付

### 8.1 补充数据没有真正并入结果
- **表现**：用户补充了缺失月份、媒体或消耗文件，结果仍然为空或总量偏小。
- **原因**：只读取主文件、工作表选错、日期/媒体键无法匹配，或合并后未复核。
- **解决**：逐个确认文件和工作表；统一日期、媒体、渠道、阶段等键；输出合并前后行数和关键总量核对，未匹配数据单独列出。

### 8.2 只给结论，没有证据表
- **表现**：汇报无法看出具体哪些日期、付费层或节点变化。
- **原因**：总结没有与可复核数据绑定。
- **解决**：每条关键结论配对应数据表，至少包含关键人数、分母、比例/金额和对照范围；先写总体，再拆付费层、渠道、日期和行为节点。

### 8.3 报告术语太抽象或图表过度设计
- **表现**：总结读起来像分析术语堆砌，图表过于商务化，重点不突出。
- **原因**：用分析师术语代替业务语言，或视觉装饰多于信息。
- **解决**：用通俗语言说清变化；图表只保留回答问题所需的系列、标签和对比；重点突出人数、金额、比例和影响节点。

### 8.4 只分析免费层，忽略付费玩家
- **表现**：结论大量描述免费玩家，付费玩家的阵容、付费深度或行为变化没有体现。
- **原因**：分析分层时没有按用户关注点安排重点。
- **解决**：用户明确关注付费玩家时，优先展开首日/累计付费档、核心 R 档和 VIP；免费层作为必要参照，不替代付费层分析。

## 9. 经验使用原则

- 这些案例是排查提示，不是自动套用的业务定义；每次仍需核对当前项目、埋点和用户本轮要求。
- 如果本文件与 Canonical 项目事实冲突，以当前用户明确要求和最新 Canonical 为准。
- 新出现的问题只有在解决方式已确认、且可复用时才加入本文件；未验证猜测应标为待确认，不能写成定论。
