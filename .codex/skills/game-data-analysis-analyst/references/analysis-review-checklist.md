# Analysis Review Checklist

在输出游戏数据分析结论、对比表或报告前执行。与 SQL Review Checklist 分工：本清单检查“数据和结论是否可信”，SQL 清单检查“查询实现是否正确”。

## 1. 问题与范围
- [ ] 已明确用户要回答的业务问题/决策。
- [ ] 项目、版本、平台、渠道、区服和时间范围正确。
- [ ] 用户要求的日期、分层、汇总行、排序和排除范围均保留。
- [ ] 分析粒度明确：玩家、账号、角色、设备、战斗、订单、关卡或事件。

## 2. 来源与数据质量
- [ ] 实际读取了用户提供的文件/查询结果，而不是只看文件名或截图。
- [ ] 文件、工作表、字段、行数和日期覆盖正确。
- [ ] 空值、零值、重复、异常类型和未匹配维表已检查。
- [ ] 数据补充文件已合并并核对，未匹配项已说明。
- [ ] 区分未上报、无行为、零值和缺失数据。
- [ ] 关键指标已从明细或分组数据复算。

## 3. 指标定义与样本
- [ ] cohort 锚点和身份键符合项目 Canonical。
- [ ] 当日、分日、累计和区间指标没有混用。
- [ ] 成熟样本条件正确；未成熟数据没有冒充完整周期值。
- [ ] 分子、分母、去重键和过滤条件明确。
- [ ] 付费留存与复购率、首日付费与累计付费、活动流水与 LTV 贡献已区分。
- [ ] 金额单位和有效支付口径已确认。

## 4. 计算与关联
- [ ] 人数按正确身份键去重。
- [ ] 事件次数没有被误当成玩家数。
- [ ] JOIN 不会产生一对多膨胀；关联前后人数/金额已对账。
- [ ] 总体率使用总分子/总分母，而非简单平均分组率。
- [ ] 总体 ARPU/LTV 使用总金额/总人数加权。
- [ ] 漏斗分子属于对应分母人群；转化率异常已排查。
- [ ] 0 次行为人群通过完整母体 + LEFT JOIN 保留。
- [ ] 末次挑战、首次行为、历史 VIP 等时间点属性取值正确。

## 5. 解释与结论
- [ ] 先确认总体变化，再拆分人群和行为节点。
- [ ] 结论能定位到具体日期、人群、关卡、活动或付费项。
- [ ] 观察事实、解释假设和因果结论已区分。
- [ ] 人数和影响范围与比例同时呈现。
- [ ] 小样本、低覆盖率和数据缺口已说明。
- [ ] 结论没有超出用户要求的观察范围。

## 6. 表格与图表
- [ ] 每个核心观点都有对应证据表或有用图表。
- [ ] 表格明确分母、样本数、观察窗口和统计口径。
- [ ] 分组顺序和字段顺序符合用户要求。
- [ ] 图表简洁、易读，不使用装饰性图表。
- [ ] 百分比使用 % 表达，避免“百分点/pct/pp”等用户不偏好的表述。
- [ ] 汇总行与分层明细能够相互对账。

## 7. 最终交付
- [ ] 先给清晰的核心结论，再给证据和方法。
- [ ] 用通俗语言说明哪里变化、哪些人变化、在哪个节点变化。
- [ ] 不把相关性写成因果。
- [ ] 未验证内容明确标记，不声称已完成未执行的查询或检查。
- [ ] 如生成 Excel/报告文件，已检查实际文件、格式、表格、图表和汇总。
