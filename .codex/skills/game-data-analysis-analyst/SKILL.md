# Game Data Analysis Analyst

适用于倍特工作室游戏项目的数据分析工作。目标不是只把数字描述出来，而是确认数据可信、口径一致、差异可解释，并把结论落到具体玩家群体、玩法节点和业务影响。

## 1. 与其他 Skill 的分工

- 本 Skill 负责：分析问题拆解、数据质量核验、指标口径理解、分群对比、漏斗诊断、业务解释、图表和报告输出。
- `game-data-sql-analyst` 负责：SQL 新建、修改、调试、性能优化和 SQL 口径实现。
- `tracking-yaml` 负责：埋点文档解析和 YAML 标准化。
- 需要 SQL 时，调用/遵循 `game-data-sql-analyst`，不要在本 Skill 内另造一套 SQL 规范；SQL 结果回到本 Skill 做数据质量与业务验证。
- 本 Skill 不代表已经连接数仓或已经执行查询。没有真实查询/文件结果时，不得声称完成了数据验证。

## 2. 知识读取与冲突优先级

每次处理项目分析任务，先读取 GitHub 当前版本，不得只凭聊天记忆或旧结论推断。

按需读取：

4. `knowledge/global/metric_definitions.md`

10. 对应项目 `*_tracking.yaml`、相关专题 `memory/projects/`、已验证 SQL 或分析文件。

不要把某次版本测试结论、临时日期筛选或一次性玩家名单写成长期规则。新确认的稳定口径应写入对应 Canonical/项目事实文件；通用分析方法或重复踩坑写入本 Skill 的 references。

## 3. 分析工作流

### 3.1 先明确问题，不要先讲结论

在分析前明确：
- 用户真正要回答的业务问题或决策。
- 项目、版本、平台、渠道、区服和时间范围。
- 分析对象粒度：账号、角色、跨渠道玩家、设备、战斗、订单、关卡或事件。
- cohort 锚点：注册/创角、首次登录、开服、活动开始、回流日等。
- 指标是当日、累计、分日还是区间汇总。
- 分子、分母、去重键和成熟样本要求。
- 用户要求的分组维度、汇总行、排序和排除范围。

用户已经明确的维度必须保留。不得擅自取消日期分组、合并分层、改变统计对象或用另一种分群替代。

如果只有一个关键口径无法从请求和仓库确定，只问一个最必要的问题；不要反复询问已知信息。

### 3.2 先确认数据是否可信

对 CSV、Excel、查询结果或导出文件：
1. 确认实际打开了正确文件，检查工作表、字段、数据范围和行数。
2. 检查日期覆盖、项目/版本/渠道筛选、空值、重复行、异常值和数据类型。
3. 确认数据粒度；识别一行代表玩家、角色、战斗、订单、事件还是分组汇总。
4. 对关键指标复算：人数、金额、比例、总计、分组汇总与明细是否一致。
5. 有补充文件时核对新增数据是否真正合并，不能因原文件缺失而忽略补充来源。
6. 区分“没有记录”“记录为 0”“字段为空”和“数据未覆盖”，不得自动把缺失当作 0。
7. 对无法验证的字段、口径或来源明确标记，不得包装成已确认事实。

不要只看截图中的局部数字就做全量结论；如果用户提供了数据文件，优先读取文件本身并检查完整范围。

### 3.3 统一指标与样本口径

- 按仓库 Canonical 指标字典解释 DAU、留存、付费率、ARPU、ARPPU、LTV、付费留存和参与率。
- D1 默认是 cohort 起始日当天；第 N 天与累计 N 天不可混淆。
- 分日成熟按对应观察日判断；不得用未成熟的部分累计值冒充成熟指标。
- cohort 日期筛选与后续事件扫描窗口是两件事；观察期必须完整覆盖。
- 付费留存默认是基准日付费 cohort 后续登录/活跃，不等于再次付费或复购。
- 首日付费分层、累计付费分层、VIP 分层是不同维度，不能混用。
- 账号、角色、跨渠道玩家、设备不能互相替代；按项目事实使用正确身份键。
- 活跃、付费、活动参与、关卡进入和战斗完成事件都按项目埋点事实确定，不跨项目照搬。
- 金额单位按项目事实确认，不得因为字段叫 payment 就假设是元或分。

### 3.4 检查统计粒度和重复计数

- 玩家人数通常按对应身份键去重。
- 战斗人数/场次应使用稳定战斗键，并按业务要求联合账号或角色去重。
- 订单流水要检查 order_id 重复和 JOIN 放大。
- 维表、标签表、渠道映射表如果不是一对一，先检查映射基数再关联。
- 漏斗每一层都应明确是事件次数还是去重玩家数。
- 漏斗分子必须是对应分母人群的子集；转化率超过 100% 时先查口径和重复，不要直接解释为异常增长。
- 合并分组或整体汇总时，优先用总分子 / 总分母重新计算，不要简单平均各组比例。

### 3.5 按层次寻找变化来源

默认顺序：
1. 总体：人数、留存、流水、付费率、ARPU、ARPPU、LTV、关卡/战斗转化。
2. 人群：首日付费档、累计付费档、VIP、媒体、渠道、平台、区服、开服天数。
3. 生命周期：新增后 D1/D2/D3/D7/D30，按用户要求分日或累计。
4. 行为节点：启动、引导、关卡进入、战斗开始、结算、重复挑战、玩法参与、道具消耗、礼包购买。
5. 结构拆解：人数结构变化、组内指标变化、付费深度变化、内容承接变化。
6. 对照验证：版本前后、测试批次、活动前后、合服前后、相近 cohort 或相近服务器。

先确认总体变化是否真实，再定位具体人群和节点。不要仅凭相关性宣称某功能、版本或渠道导致指标变化。

### 3.6 形成可复核的结论

每个关键结论都应能回答：
- 哪里变了？
- 哪些玩家/渠道/付费层变了？
- 在哪个日期、关卡或行为节点变了？
- 对人数、付费、留存或长期价值有什么影响？
- 数据能支持到什么程度，还有什么不能确认？

把观察事实、解释假设和建议分开。没有对照或因果证据时使用“同时出现”“更可能与……有关”“需要进一步验证”，不要写成确定因果。

## 4. 重点分析场景

### 留存、付费与 LTV
- 明确 cohort、成熟窗口、有效流水、金额单位和分母。
- 总体 LTV = 对应 cohort 累计有效流水 / cohort 玩家数。
- 合并服务器、媒体或付费层时，整体 LTV/ARPU 按总金额除以总人数加权，不平均分组 LTV。
- 如果“活动 LTV 贡献”与“活动流水贡献”不是同一指标，必须写清公式和收入范围。活动流水为 0 但 LTV 贡献非 0 时，先检查是否混入全量收入、分母或时间窗口不一致。
- 付费率、付费留存、复购率要分别命名，不可混为一谈。

### 关卡、战斗与漏斗
- 先构建进入关卡/节点的玩家全集，再关联后续战斗或玩法事件。
- 对玩家-关卡维度去重；事件次数不能直接当人数。
- 分析“末次挑战”时，按该玩家该关卡的实际战斗时间选最后一个 battle_uid；只有确认 battle_uid 单调递增时才可用其排序。
- 统计肉鸽次数等可选行为时，未触发行为事件不代表未进入关卡。先保留所有进入关卡的玩家，再 LEFT JOIN 行为次数，空值按业务定义补为 0。0 次人数与进入关卡人数应能对账。
- 区分首次挑战、末次挑战、累计挑战和所有挑战；不要混用。
- 失败后重试、失败后流失、直接退出下一关要分开统计；明确“失败人数”“重复挑战人数”“未再进入人数”的分母。
- 每个关卡的下一节点转化分子应是上一节点玩家集合中的后续到达人数，避免不同 cohort 或不同身份粒度造成转化率超过 100%。

### 战斗伤害与异常值
- 用户问整场战斗总伤害时，按战斗内所有角色/单位的伤害明细汇总；不要只取某个 role_id 或单个角色伤害。
- 明确战斗级、角色级、受击目标级的统计粒度；城墙受击伤害与整场输出伤害不是同一指标。
- P50/P75/P99/最大值必须基于同一有效样本，并说明分组维度（如关卡、VIP、付费档）。
- 需要战斗发生时 VIP 时，按战斗时间匹配历史 VIP 快照；缺少历史 VIP 记录按项目规则处理（已确认场景为 VIP0），不能用当前 VIP 覆盖历史。
- 空字符串、NULL、异常类型值先清洗和核查，再参与数值计算。

### 活动与资源
- 活动参与要依据真实业务定义：登录/打开页面不一定等于参与；若定义为道具消耗，应使用对应 item ID 和消耗日志，并核对 item_log、money_log 等来源。
- 道具获得与消耗要区分；同一道具的产出、消耗、领取不能混为一类。
- 活动金额、活动参与人数和活动 LTV 贡献必须分别定义。
- 商品名、product_id、道具 ID 映射不完整时，先输出未匹配清单，不要静默归入其他类别。

### 合服、版本和活动前后对比
- 合服效果默认按“合服前一周 → 合服周 → 合服后一周”比较；合服周要包含合服日，除非用户另有定义。
- 如果用户要求按合服日期分组，就以合服日期为分组键，不要擅自按 zone_id 分组。
- 前/中/后观察窗口作为对比列，不要把它们再拆成额外分组维度，除非用户明确要求。
- 跨服务器整体指标按人数/金额加权；不能直接平均每服 LTV、ARPU 或留存率。
- 版本测试对比要保证日期、成熟样本、渠道、平台和付费层口径一致；启动、首战、引导、关卡等链路要分节点比较，不把总体转化差异直接归因于单一节点。

### 英雄上阵与付费分层
- 战斗总场次按账号 + battle_uid 等稳定战斗键去重；英雄上阵场次也按同一战斗键去重，不以英雄明细行数代替战斗数。
- 上阵率分子与分母应使用同一战斗总体。
- 用户要求按天、付费档拆分时，必须保留这些维度；不要只写免费玩家或总体结论而遗漏付费玩家核心阵容。
- 英雄品质/星级、历史上阵和当前养成状态不是同一概念。需要历史状态时应使用历史事件/快照，不用当前属性倒推过去。

## 5. 报告与表格输出规范

- 先给 3–4 条最重要结论，再展开证据；结论要通俗、具体，避免空泛术语。
- 每个核心观点尽量配一张对应数据表，列出日期/人群/分母/人数/比例或金额；让读者能直接复核。
- 用户要求分天、分层、分渠道或分服务器时，逐项展示，不擅自汇总掉关键维度。
- 对比数据应明确观察窗口、样本数、分母、加权方式和未成熟范围。
- 百分比展示直接使用 %。遵循用户已确认习惯，尽量不使用“百分点”、pct、pp 等表达；描述率变化优先写“从 x% 升至 y%”，若表达相对变化则明确写“相对增长/下降 x%”。
- 图表简洁、易读，避免过度商务化或装饰性设计。优先用能直接回答问题的图表；不为凑图而画图。
- 汇总行和分层行按用户要求完整提供；表格列顺序按用户指定，不随意重排。
- 用户明确要求只分析某个观察范围（如 D60 之前）时，不延伸分析被排除区间。
- Excel 输出使用清晰一致的格式。颜色应有明确含义；没有明确状态含义时使用中性样式，不要用填色暗示“已修改”或“异常”。
- 结论应指出人数和影响范围，不只写比例；小样本或低覆盖率要说明。

## 6. 常见异常的诊断顺序

### 查询结果为空
依次核查：项目/表后缀 → 日期分区和时区 → 事件名 → 字段名 → 环境过滤 → 身份键和 JOIN → 数据类型 → 渠道/付费/关卡筛选 → 成熟条件。先用小范围明细验证事件是否存在。

### 人数或流水突然翻倍
检查：明细 JOIN 是否一对多、角色与账号粒度是否混用、订单是否重复、battle_uid 是否联合账号去重、维表是否重复映射、payment 与 token_payment 是否重复相加、金额单位是否重复换算。

### 转化率超过 100%
检查：分子分母是否同一 cohort、身份键是否一致、分子是否去重、事件重复是否放大、JOIN 是否一对多、是否把事件次数当玩家人数。修正后验证分子集合是分母集合的子集。

### 0 次行为人数异常
检查：是否仅从行为事件表出发导致无行为记录的人消失。先以进入节点/活跃人群作全集，再 LEFT JOIN 行为聚合并按规则补 0。

### 指标有金额但人数为 0，或有 LTV 贡献但活动金额为 0
检查：金额和人数是否来自同一事件、同一 cohort、同一时间窗、同一商品口径；检查 JOIN 后的 NULL 和过滤条件。明确该“贡献”是否实际包含全量流水。

### 结果与截图/另一张报表不一致
不要先认定哪张表正确。先对齐项目、日期、数据粒度、去重键、分子分母、成熟样本、渠道、金额单位和过滤条件，再用同一明细口径复算。

## 7. 最终交付前检查

执行 `references/analysis-review-checklist.md`，并按具体场景查看 `references/analysis-lessons.md`。

默认输出：
1. 关键结论（简洁、明确）。
2. 对应数据表/图表和口径说明。
3. 异常、限制和未确认项。
4. 有证据支持的下一步检查或建议。

不要重复罗列过程，不要把推测写成事实，也不要在没有真实数据时编造示例结果。

## 8. 知识沉淀

- 专题临时但可复用口径：更新 `memory/projects/` 专题文件。
- 多次出现的分析方法、数据质量问题和解决方式：更新本 Skill 的 `references/analysis-lessons.md`。
- 修改后同步更新索引/README 中必要的入口，不复制整份规则到多个文件。
- 不提交账号、密码、token、业务导出数据、截图或临时查询结果。
