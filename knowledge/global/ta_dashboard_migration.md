# 数数 TA 跨项目迁移看板

status: current
last_verified: 2026-11-16

## 导出、比对与导入

1. 在源项目「看板」左侧加号菜单选「导出看板」，展开项目空间，只勾选要迁移的看板。导出的 JSON 可用来核对报表模型、动态参数、看板筛选、卡片尺寸和位置。
2. 先核对目标项目的分析主体、事件、属性类型和枚举，再改配置。检查公式里的表达式和依赖对象两处引用，以及分组、事件拆分、指标筛选、全局筛选和看板默认筛选。SQL 报表还要核对写死的项目表名、维表、金额单位和时间戳类型。
3. 保留源报表模型。原生留存、LTV 和基于留存的增长指标用「留存分析」，礼包分布用「事件分析」，原本是 SQL 的报表按实际依赖适配。留存要逐项比对初始事件、回访事件、同时展示指标及各自筛选、观察窗口、成熟批次和分组。查询成功之后还要验证业务口径。
4. 在目标项目的加号菜单选「导入看板」。导入可创建项目空间，同名空间或报表可能出现编号后缀。若已有正式看板，用「添加内容 → 已存报表」挂载验收通过的报表。同一报表可被多张看板引用，移除卡片与删除报表是不同操作。

## 虚拟属性与标签

- 在「数据 → 数据管理 → 事件属性 → 虚拟事件属性」选择返回类型，填写公式并完成「校验 → 调试 → 保存」。再到列表确认属性可用，在实际报表里验证它在相关事件上的覆盖。调试输入为空时返回空值，只说明公式可以执行。
- 在「用户 → 用户标签」先选与报表一致的分析主体。条件标签可按行为和金额阈值分层，规则排序决定重叠条件优先命中的档位。SQL 标签返回两列，第一列为唯一的分析主体 ID，第二列为标签值。先预览，再保存并等待计算完成。使用事件表时加上日期分区。
- 虚拟事件属性可通过 `ta_tag."标签名"` 引用已算好的标签。对“截至事件发生时是否付费”一类筛选，应比较首次有效付费时间和事件时间。直接引用当前累充金额会将后续付费带入历史事件。
- 验证留存分组时，在结果表展开「阶段值」或具体日期的加号，看「分组详情」中的实际标签值和人数。默认折叠的汇总行及图例中的「未分组」不足以判断整个标签是否失效。标签手动更新、自动更新及历史日期版本要分别核对。

## 看板验收与清理

- 保存后从目标看板重新打开，核对每张卡片的报表模型、实际结果、分组、顺序、标题和表格样式。可再次导出配置，对比 `reportMappings` 和 `ui_config.layout`。卡片顺序按网格位置核对。卡片「更多 → 大图」可调整为整行，保存后复核；部分「合计」表格的样式控件在界面中禁用。
- 正式空间保留一套看板。更换卡片时先挂载并验证新报表，再移除旧卡片。清理前在「报表管理」核对「应用看板数」和「应用看板」，只清理确认属于本次迁移且引用数为零的旧报表。删除报表不可恢复，先确认清理范围。删除项目空间会把其中仍有的资产移到个人空间，清理空的临时空间前先核对内容。
